# Выбор рабочей директории из UI (WorkspaceHub)

Дата: 2026-07-30. Статус: одобрено в брейншторме, ждёт implementation-плана.

## Задача

Запустил `svarog serve` один раз — дальше рабочая папка выбирается в браузере,
как проект в Claude Code: «Новый чат» → выбрать каталог → агент работает в нём
со **своим** конфигом (память, скиллы, модели этого проекта). Сейчас workspace
жёстко фиксируется на старте `serve` (`cli/main.py`), а named workspaces
(ADR-0017) живут только под корнем сервиса и в существующий проект вне корня не
ведут.

## Решения, принятые в брейншторме

| Вопрос | Решение |
|---|---|
| Что выбираем | Любую папку на машине (не только named workspaces) |
| Область выбора | На сессию, с собственным конфигом корня (мультиплексор — подход C) |
| Граница доступа | Без белого списка, но фича существует **только в single-tenant**; в multi-tenant/cloud выключена полностью |
| Момент выбора | При создании сессии; папка фиксируется на всю жизнь сессии, смены на лету нет |
| Механика UI | Все три: недавние + обзор ФС + ввод пути с автодополнением, на одном экране |

Проговорённое следствие: два чата в разных корнях могут работать одновременно —
мультиплексор допускает это по построению, отдельный ограничитель не закладываем
(параллельные чаты как продуктовая фича остаются отложенными, но архитектурно
дверь открыта).

## Архитектура: `WorkspaceHub`

Новый класс в `gateway/hub.py` по прямому образцу `TenantHub`, ключ — путь:

```
WorkspaceHub
  base_cfg: SvarogConfig            # конфиг, загруженный на старте serve
  default_root: Path                # папка запуска svarog serve
  _services: dict[Path, GatewayService]   # ленивая материализация
  _registry: WorkspaceRootsRegistry # ~/.svarog/workspace-roots.json
```

- `service_for(path)`: нет сервиса → `load_config(project_dir=path)` →
  `GatewayService(cfg, path)`. Каждый корень получает свой cfg, память, скиллы;
  если проект оверрайдит `db_path` (скаффолд ставит `./.svarog/svarog.db`) —
  и свою БД.
- Реестр корней: JSON в `~/.svarog/workspace-roots.json` — известные корни
  (путь → last_used) плюс карты маршрутизации `session_id → root` и
  `run_id → root`. Реестр — **кэш маршрутизации, не источник истины**:
  восстановим из `Session.meta["root"]`.
- Auth не меняется: хаб оборачивается той же bearer-проверкой, что
  `SingleTenantResolver` (реализует протокол `GatewayResolver`).
- В multi-tenant режиме (`tenancy.enabled`) `WorkspaceHub` не создаётся,
  CLI-ветка остаётся нетронутой.
- Shutdown: обход материализованных сервисов, `close_warm_sessions()` каждому —
  как `TenantHub.shutdown`.

## Маршрутизация

Правило: **сессионные и run-эндпоинты — по id; workspace-эндпоинты — по явному
корню; дефолт — корень запуска serve.**

- **Создание.** `CreateSessionRequest` и `CreateRunRequest` получают
  `path: str | None`. Задан → `service_for(path)`, нет → сервис `default_root`.
  Хаб записывает `session_id → root` / `run_id → root` в реестр (симметрично
  `on_run_created` добавляется `on_session_created`). Путь дублируется в
  `Session.meta["root"]` — запись самодостаточна.
- **Сессионные вызовы** (`GET /sessions/{id}`, сообщения, WS,
  `POST /runs/{id}/...`): id → реестр → сервис. Промах реестра →
  `default_root`; все сессии, созданные до фичи, работают без миграции.
- **Workspace-вызовы** (`/config`, `/secrets`, `/memory`, `/skills`,
  `/models`): опциональный заголовок `X-Svarog-Root`. UI в сессии шлёт её
  корень — экран настроек показывает конфиг того проекта. Без заголовка —
  `default_root` (текущее поведение).
- **`GET /sessions`** (агрегированный список): веер по сервисам всех корней
  реестра, склейка. Корни без локального `db_path` делят `~/.svarog/svarog.db` —
  одна сессия видна из нескольких сервисов; дедупликация по `session.id`,
  корень из `meta["root"]`. Материализация сервиса при листинге дешёвая
  (объект + соединение с БД; контейнеры — только под run).
- **`GET /fs?path=...`** — эндпоинт самого хаба, только single-tenant:
  подкаталоги для обзора и автодополнения.

## Жизненный цикл и краевые случаи

- **Рестарт serve.** Реестр переживает рестарт. Refuel-супервизор — по образцу
  `TenantHub.run_supervisor`: обходит корни с записанными run'ами,
  `supervise_once`, ошибка одного корня не рвёт цикл. Resume находит корень
  через реестр.
- **Валидация пути.** `expanduser` + `resolve()`; путь обязан существовать и
  быть каталогом, иначе 422 с внятным текстом. Вложенные корни (`~/proj` и
  `~/proj/test`) легальны — два независимых сервиса; общую БД закрывает
  дедупликация.
- **Корень исчез.** Сессионный вызов → 410 Gone («каталог сессии удалён»).
  В «недавних» несуществующие пути приглушены и некликабельны; из реестра
  чистятся лениво при следующей записи, без фонового GC.
- **Реестр побился/потерян.** Маршрутизация падает на `default_root`, корни
  восстанавливаются из `Session.meta["root"]` по мере обращения.
- **`GET /fs`.** Только каталоги; скрытые (`.*`) отфильтрованы;
  `PermissionError` на подкаталоге помечает его недоступным, а не валит листинг
  в 500. Дефолтная точка входа — `$HOME`.
- **YAGNI (сознательно нет):** выселение простаивающих сервисов (тёплые
  sandbox'ы гасятся только на shutdown), лимит числа корней, смена папки у
  живой сессии, миграция старых сессий.

## UI

Поток: «Новый чат» → экран `WorkspacePicker` → чат. Три механики на одном
экране, пишут в одно состояние-«кандидат»; подтверждение →
`POST /sessions {path}`.

1. **Поле пути с автодополнением** — вверху, в фокусе. Подсказки подкаталогов
   по префиксу из `GET /fs`. Переиспользуем `Completion.tsx` (дебаунс,
   ARIA-комбобокс) — второй комбобокс не пишем.
2. **Недавние** — корни реестра по last_used; обычный случай — один клик.
   Несуществующие приглушены.
3. **Обзор** — колоночная навигация: хлебные крошки + список подкаталогов;
   клик — спуск, крошка — подъём, кнопка «Выбрать эту папку». Дерева с
   раскрытием нет.

Шапка чата показывает корень сессии (только отображение). Строки списка сессий
получают бейдж корня — одноимённые чаты разных проектов различимы.

Клиент:

- `api/types.ts`: `SessionView.root: string`, `CreateSessionRequest.path?`,
  типы `/fs`.
- `api/client.ts`: метод `fs(path)`; `X-Svarog-Root` из активной сессии для
  workspace-экранов.
- Ошибки: 422 — инлайн под полем ввода; 410 — плашка в чате с предложением
  выбрать другую папку.

## Тесты

- Хаб: маршрутизация по id, промах реестра → `default_root`, дедуп общей БД,
  восстановление после потери реестра, shutdown гасит все сервисы.
- `GET /fs`: листинг, фильтр скрытых, `PermissionError`, отсутствие эндпоинта
  в multi-tenant.
- Валидация `path` при создании: файл/несуществующий/пустой → 422.
- 410 на исчезнувший корень.
- `WorkspacePicker.test.tsx`: три механики, состояние-кандидат, инлайн-ошибки,
  недоступные «недавние».

## Явно вне объёма

- Multi-tenant/cloud: фича выключена, `/fs` и `path` не существуют.
- Белый список корней — нет (осознанное решение single-tenant).
- Смена папки существующей сессии, параллельность как продуктовая фича,
  выселение сервисов — позже, если понадобится.
