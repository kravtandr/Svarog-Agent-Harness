# Нативный цикл видит изображения и читает документы

**Дата:** 28 июля 2026
**Статус:** утверждён
**Контекст:** вложения к сообщению (`2026-07-28-composer-completion-and-uploads-design.md`)

## Задача

Живая проверка вложений показала, что обещание «прикрепи скриншот — агент
увидит» выполняется только при `executor.type: external`. Нативный цикл
ответил дословно: «у меня нет инструмента для чтения изображений»,
вызвал `read_file` и получил «файл не является текстовым».

## Почему так вышло

Два независимых пробела, и оба были не видны из тестов.

**Инструментов нет в реестре нативного цикла.** `ReadImageTool` и
`ReadDocumentTool` регистрируются только в `runtime/bridge_control.py:173`
— в мосте внешнего агента. `runtime/run_assembly.py` их не добавляет.

**Даже с регистрацией картинка бы не дошла.** `ToolResult.blocks` читает
единственное место — `bridge_control.py:263`, откуда блоки уходят
внешнему агенту как MCP-контент. Нативный цикл кладёт в историю
`ChatMessage(role="tool", content=rendered)` (`loop.py:536`), где
`rendered` — текст, а `ChatMessage` несёт только строку. Провайдер строит
запрос как `{"role": …, "content": msg.content}`
(`openai_compatible.py:70`). Картинка была бы отброшена молча.

Спек вложений утверждал, что `read_image` — это путь к модели. Инструмент
существует; в чей реестр он попадает, проверено не было.

## Решение

### 1. Изображения в `ChatMessage`

```python
@dataclass(frozen=True)
class ImageRef:
    """Ссылка на изображение в workspace, а не его байты."""
    path: str          # относительно workspace
    mime: str


@dataclass
class ChatMessage:
    role: Role
    content: str = ""
    tool_calls: tuple[ToolCallRequest, ...] = ()
    tool_call_id: str | None = None
    images: tuple[ImageRef, ...] = ()
```

**Ссылка, а не байты — решающее ограничение.** `LoopState.messages`
сериализуется в checkpoint после каждого вызова инструмента
(`checkpoint.py:63`). Пятимегабайтная картинка — это ~6.7 MB base64 в
*каждом* сохранении. Ссылка занимает сотню байт, а файл и так лежит в
`.attachments/` рабочего дерева и переживает resume.

Base64 материализуется один раз, при сборке запроса к провайдеру, и в
истории не оседает.

### 2. Доставка: отдельное user-сообщение, не tool

Openai-совместимый контракт принимает части `image_url` только в
сообщениях роли `user`; сообщение роли `tool` несёт строку. Поэтому цикл,
получив результат с блоками, в итоге добавляет **два** сообщения — но не
подряд одним обработчиком одного вызова, а с буфером через весь ход
(поправка после финального ревью, находка 1; исходная версия ниже
рассуждала только про один tool call за ход и была багом):

```python
state.messages.append(ChatMessage(role="tool", content=rendered, tool_call_id=call.id))
if images:
    state.pending_images = (*state.pending_images, ChatMessage(
        role="user", content=f"Изображение из {call.name}:", images=images
    ))
```

Ассистентский ход может нести несколько tool calls (`state.pending_tool_calls`
дренируется циклом `while` в `_execute_pending`, батчем или по одному); если
бы user-сообщение с картинкой дописывалось в `state.messages` сразу после
первого же результата, оно оказалось бы МЕЖДУ tool-ответами одного хода —
openai-совместимый контракт требует, чтобы соседние tool-сообщения одного
хода шли без ничего постороннего между ними, и это 400, который
`assert_history_valid` не ловит (он балансирует счётчики `tool_call_id`, а
не порядок). `read_image` — `is_read_only`, то есть конкурентно-безопасен и
естественно попадает в батч с любым другим чтением: «покажи скриншот и
прочитай тот файл» — типичный ход с этой формой.

Правильно: копить ноты в `state.pending_images` (поле `LoopState`,
переживает checkpoint) и переносить их в `state.messages` одним куском
только когда `state.pending_tool_calls` полностью дренирован — то есть
после хода целиком, а не после каждого отдельного результата. Порядок
tool-перед-image по-прежнему обязателен: без tool-сообщения ход остаётся
без ответа на `tool_call_id`, и провайдер отклонит запрос — просто теперь
между «tool этого хода» и «image этого хода» не может влезть tool-ответ на
другой вызов того же хода.

### 3. Рендер запроса

`_to_openai_messages` при непустом `images` строит `content` массивом
частей:

```python
{"role": "user", "content": [
    {"type": "text", "text": msg.content},
    {"type": "image_url", "image_url": {"url": f"data:{mime};base64,{b64}"}},
]}
```

Файл читается по `ImageRef.path` относительно workspace run'а. Пропавший
файл не роняет запрос: часть заменяется текстом «изображение
{path} недоступно», и модель узнаёт об этом словами.

### 4. Экономика контекста

Изображение стоит на порядок дороже своего текстового описания, а история
растёт. В запрос попадают **только два последних** изображения; более
ранние `ImageRef` вырождаются в текст «изображение {path} (показано
ранее)». Константа `MAX_IMAGES_IN_CONTEXT = 2` — модульная константа
`llm/openai_compatible.py`, а не поле конфига рядом с прочими лимитами
`runtime`.

Это то же соображение, что стоит за `runtime.tool_output_context_chars`:
данные не теряются (файл на месте, агент может перечитать), но контекст не
раздувается неограниченно.

### 5. Провайдер без vision

Надёжного признака поддержки у произвольного openai-совместимого endpoint
нет, и гадать по имени модели — хуже, чем не гадать. Поэтому запрос
уходит как есть, а ошибка провайдера (обычно 400) поднимается с
пояснением: модель не приняла изображение, попробуйте другую или
внешнего агента. Пояснение добавляется только когда в запросе были
изображения — иначе оно вводило бы в заблуждение.

### 6. Регистрация инструментов

В `run_assembly.py`, рядом с `file_tools`:

```python
registry.register(ReadImageTool(self._workspace))
if document_tools_available():
    registry.register(ReadDocumentTool(self._workspace))
```

`read_document` — под условием: он требует опциональной группы `docs`
(markitdown), и `bridge_control.py:175` уже регистрирует его так же.
`read_image` зависимостей не имеет.

## Обработка ошибок

| Ситуация | Поведение |
|---|---|
| Файл изображения исчез между вызовом и запросом | Часть заменяется текстом, запрос уходит |
| Провайдер отклонил изображение | Ошибка провайдера + пояснение про vision |
| Изображение больше 5 MB | `read_image` отказывает как сейчас, до попадания в историю |
| markitdown не установлен | `read_document` не зарегистрирован; `read_image` работает |

## Тесты

**Ядро.** `ChatMessage` с `images` сериализуется в checkpoint без base64 и
восстанавливается ссылкой. `_to_openai_messages`: без изображений
`content` остаётся строкой (обратная совместимость всех существующих
вызовов); с изображениями — массив частей с корректным `data:`-URI;
пропавший файл даёт текстовую замену, а не исключение. Ограничение в два
изображения: третье вырождается в текст, причём вырождаются **старшие**,
а не свежие.

**Цикл.** Результат с блоками кладёт в историю два сообщения в верном
порядке; результат без блоков — одно, как раньше. Пояснение про vision
добавляется к ошибке провайдера только когда изображения были.

**Реестр.** `read_image` зарегистрирован в нативном цикле всегда;
`read_document` — только при доступном markitdown.

**Сквозной.** Прогон с фальшивым провайдером, который проверяет, что до
него дошёл `image_url` с ожидаемым `data:`-URI. Это единственный тест,
доказывающий, что картинка проходит весь путь от файла до запроса.

## Что не делается

- Определение vision-способности модели заранее. Каталог OpenRouter несёт
  модальности, произвольный провайдер — нет; половинчатая проверка хуже
  честной ошибки.
- Изображения в сообщении **человека** (а не в результате инструмента).
  Композер по-прежнему шлёт путь, а не картинку; путь к модели —
  `read_image`. Это осознанно: так работает и внешний агент, и незачем
  иметь два разных механизма.
- Автоматическая конвертация PDF в картинки. `read_document` берёт
  текстовый слой; скан без слоя — задача агента через `pdftoppm`, как
  сказано в подсказке инструмента.
