# Retrieval памяти через SQLite FTS5 (связка B, #2)

**Дата:** 2026-07-24
**Статус:** реализовано (связка B)
**Скоуп:** связка B из пятёрки улучшений памяти — релевантный retrieval поверх
memory-wiki. Связка A (профиль/автозахват/Dream) — уже в `main`, вне этого
спека.

## Проблема

После связки A память навигируема (index.md + прогрессивная загрузка через
`read_memory`), но при росте числа страниц два потолка остаются:

- агент находит страницу только по **заголовку** в `index.md`; по содержимому
  («где я договаривался про версионирование API?») найти нельзя;
- при переполнении `index.md` (`render_index`, лимит `index_max_lines`) хвост
  каталога **сворачивается по `updated`-дате** — релевантные, но давно не
  трогавшиеся страницы молча выпадают из виду.

Ограничение инфраструктуры (ADR-0001): только Git + SQLite, без внешних
сервисов. **FTS5 — часть SQLite** (кириллица через `unicode61` подтверждена),
поэтому полнотекстовый индекс укладывается в ограничение, а векторная БД — нет.

## Ключевые решения (зафиксированы в брейншторме)

1. **Две формы retrieval:** agent-driven tool `search_memory` **и**
   авто-инъекция релевантного на старте run'а.
2. **Авто-инъекция — только при переполнении** индекса: на малой памяти
   поведение не меняется; FTS включается там, где сейчас теряется хвост.
3. **Индекс в runtime-БД, не в Git** — производное, перестраиваемое состояние
   (как trace); синхронизирует единственный writer в `_reindex`.
4. **Общее ядро `MemoryIndex`** — один источник правды по FTS для writer'а,
   tool'а и авто-инъекции.
5. **Dream тоже получает `search_memory`** (ищет дубли/противоречия).

## Решение

### FTS-индекс и `MemoryIndex`

FTS5-виртуальная таблица `memory_fts(path, content)` в runtime-БД
(`.svarog/svarog.db`). В Git не коммитится, перестраиваема из файлов памяти.

Класс `MemoryIndex` (`memory/index.py`) инкапсулирует весь FTS:

- `ensure_schema()` — лениво создаёт таблицу (без Alembic-миграции: таблица
  производная и перестраиваемая, в отличие от доменных);
- `sync(changed_paths, deleted_paths)` — upsert изменённых файлов и удаление
  пропавших; вызывается из writer'а;
- `rebuild()` — полный ребилд из `memory/**/*.md` (ленивый: если таблица
  пуста/отсутствует, или память правили в обход writer'а);
- `search(query, limit)` — `MATCH` + ранжирование `bm25()`, возвращает список
  `(path, snippet, rank)` (сниппет — через FTS5 `snippet()`).

**Что индексируется:** по строке на файл памяти, **кроме** автоген
(`index.md`, `log.md` — навигация, не контент) и `user/profile.md` (всегда в
контексте). То есть `projects/*/*.md`, `decisions/*.md`, `sources/**`, заметки.
Токенайзер — дефолтный `unicode61` (стемминг русского — YAGNI, не тащим).

**Свежесть:** синхронизирует единственный writer в `MemoryWriter._reindex`
(запускается после каждого дренажа под writer-локом, ADR-0004, сразу после
`regenerate_index`): `index.sync(...)` изменённых/удалённых путей. Консистентно
по построению — гонок нет.

**Изоляция:** индекс ключуется путём внутри одного memory-репо; per-tenant
scoping мультиарендности — вне скоупа, отмечено как будущее.

### Tool `search_memory`

`search_memory(query: str, limit: int = 5)` — read-only, риск LOW, без approval
(как `read_memory`). Делегирует в `MemoryIndex.search`, возвращает top-N:
`путь + сниппет + ранг`. Агент по пути подтягивает полную страницу через
`read_memory` — search находит *где*, read_memory даёт *целиком*.

- **Доступ к БД:** tool получает session-factory runtime-БД (инъекция в
  `run_assembly._build_registry`, рядом с `ReadMemoryTool`), открывает короткую
  read-сессию на поиск — FTS в той же sqlite, конкурентные читатели безопасны.
- **Санитизация:** сырой `query` может содержать спецсинтаксис FTS5 → падение
  `MATCH`. Оборачиваем как терминный запрос (экранируем токены); при ошибке —
  «уточни запрос», не исключение. Пусто → «ничего не найдено».
- **Регистрация:** в `_build_registry` рядом с `ReadMemoryTool`; в DREAM-профиле
  тоже (Dream ищет дубли/противоречия).

### Авто-инъекция релевантного (при переполнении)

**Триггер:** когда `render_index` переполняет `index_max_lines` и сворачивает
хвост по дате. `render_index` возвращает флаг «переполнено».

**Что:** при переполнении FTS-ранжируем страницы против **текущей задачи** и
добавляем блок «# Релевантно задаче» с top-K (`fts_inject_pages`, путь +
сниппет) под байтовым бюджетом (`fts_inject_bytes`). profile + свёрнутый index
остаются — навигация цела, релевантные страницы с упавшего хвоста всплывают.
Нет переполнения → блока нет (старое поведение). Нет совпадений / ошибка FTS →
пропуск (best-effort, run не падает).

**Интеграционная тонкость:** блок task-зависим, а задача известна в `loop.run`,
тогда как базовая память читается в `build_loop` (до задачи). Поэтому:

- базовое чтение (profile + index) остаётся в `build_loop` как есть;
- **task-ранжированный блок считается в `loop.run`** через `MemoryIndex`,
  только при переполнении, и дописывается к memory-секции промпта. `AgentLoop`
  получает `MemoryIndex` + `mem_dir` + флаг переполнения.

**Внешние executor'ы:** тот же блок префиксит memory-контекст в
`prepare_agent_launch` (как персона-директива связки A) — там задача доступна
на старте.

## Конфигурация

В `MemoryConfig` (`config/schema.py`):

```yaml
memory:
  fts_enabled: true          # тумблер FTS (синк добавляет малую цену дренажу)
  fts_inject_pages: 5        # K страниц в блоке авто-инъекции
  fts_inject_bytes: 3000     # байтовый бюджет блока
  # index_max_lines (существующий) — сигнал переполнения для авто-инъекции
```

## Обработка ошибок (fail-soft — run никогда не падает)

- sqlite без FTS5 (редко) → индекс отключается, `search_memory` отвечает «поиск
  недоступен», авто-инъекции нет (лог-варнинг);
- кривой `MATCH` → санитизация; при ошибке — «уточни запрос»;
- рассинхрон (память правили в обход writer'а) → ленивый `rebuild`, если
  таблица пуста/отсутствует; иначе её держит свежей `_reindex`;
- контент секретобезопасен по построению — writer secret-сканит перед
  коммитом, секреты в память не попадают.

## Тестирование

По образцу `tests/test_memory_*.py`:

- **`MemoryIndex`:** `ensure_schema`; `sync` (upsert/delete); ранжирование
  `bm25`; `snippet`; `rebuild` из файлов; кириллический запрос; санитизация
  (спецсимволы не роняют).
- **`SearchMemoryTool`:** пути+сниппеты; пусто → дружелюбно; кривой запрос →
  дружелюбно.
- **Writer↔FTS (интеграция):** `apply` изменение → `_reindex` синкает →
  `search` находит; удаление → пропадает из индекса.
- **Авто-инъекция:** переполнение → блок с релевантной страницей появляется;
  нет переполнения → блока нет; нет совпадений → нет; байтовый бюджет соблюдён.
- **`render_index`:** возвращает корректный флаг переполнения.
- **Конфиг:** дефолты `fts_enabled=true`, `fts_inject_pages=5`,
  `fts_inject_bytes=3000`.

## Затрагиваемые файлы

- `memory/index.py` (новый) — `MemoryIndex` (schema/sync/rebuild/search).
- `memory/writer.py` — `_reindex` вызывает `index.sync`.
- `memory/wiki.py` — `render_index` возвращает флаг переполнения.
- `tools/memory_tools.py` — `SearchMemoryTool`.
- `runtime/run_assembly.py` — регистрация tool'а + проводка `MemoryIndex`;
  task-блок в `prepare_agent_launch`.
- `runtime/loop.py` — `AgentLoop` получает `MemoryIndex` + флаг; task-блок в
  `loop.run`.
- `config/schema.py` — `MemoryConfig` FTS-поля.

(Отдельный ADR по FTS-выбору — опционально; решение «FTS5 вместо вектора ради
Git+SQLite» уже зафиксировано в ADR-0001/этом спеке, дублировать не обязательно.)

## Отличия реализации от этого дизайна

Зафиксировано при исполнении плана — дизайн намеренно не переписан задним
числом, чтобы расхождения были видны.

1. **Полный ребилд вместо инкрементального `sync`.** Здесь спроектирован
   `MemoryIndex.sync(changed_paths, deleted_paths)`; реализован модуль-функция
   `reindex(session, memory_dir)` — `DELETE` + перечитывание всех
   индексируемых файлов на каждом дренаже. Проще и заведомо консистентно, но
   цена растёт линейно с числом страниц. Инкрементальный синк — очевидная
   первая оптимизация, когда память вырастет.
2. **Модуль вместо класса.** `MemoryIndex` как класс не понадобился: состояния
   у него нет, сессия приходит параметром. Функции `ensure_schema` / `reindex`
   / `search` / `sanitize_query` живут в `memory/index.py`.
3. **Ленивый `rebuild` при рассинхроне не реализован.** Раздел «Обработка
   ошибок» обещает ленивый ребилд, если таблица пуста или отсутствует; в плане
   такой задачи не было. Следствие: на памяти, наполненной в обход writer'а
   (например, свежий клон memory-репо), поиск молча пуст до первого дренажа.
4. **Блок авто-инъекции не переживает refuel.** Он считается в `loop.run`;
   `_rebuild_after_refuel` пересобирает контекст из `task_state.md` и блок
   теряет. Точка расширения готова — `AgentLoop._memory_for(task)`.
5. **Санитизация даёт конъюнкцию.** Все токены запроса становятся
   обязательными, поэтому служебные слова модели («где», «OR») сужают выдачу.
   Закреплено тестом `test_search_is_conjunctive_over_tokens`.

## Явно вне скоупа

- Векторный поиск / эмбеддинги (нарушает Git+SQLite, ADR-0001).
- Стемминг/морфология русского (кастомный токенайзер) — YAGNI.
- Per-tenant scoping FTS-индекса (мультиарендность) — будущее.
- Чанкинг по секциям (сейчас — строка на файл); секционные сниппеты — позже.
- Авто-инъекция — native-only; внешние executor'ы получают retrieval через
  `search_memory` в бридже (там задача известна агенту, отдельный блок не нужен).
