# Гиперперсонализация: типизированный профиль, автозахват фактов, Dream по профилю

**Дата:** 2026-07-24
**Статус:** реализовано (связка A; ADR-0021)
**Скоуп:** связка A из пяти пунктов улучшения памяти — про профиль
пользователя. Пункты: #3 типизация профиля, #1 автозахват фактов, #4 curator
по профилю (растворён), #5 Dream по профилю. Связка B (#2 FTS5-retrieval) —
отдельный цикл, вне этого спека.

## Проблема

Память Svarog надёжно *хранит* факты, но не поддерживает гиперперсонализацию
как поведение:

- `user/profile.md` — плоский свободный текст без контракта. Предпочтения
  нельзя достать адресно, и они подаются модели как «факты», а не как
  инструкция поведения (пробел «факты ≠ поведение»);
- запись в память — только по явному вызову `remember` основной моделью. Если
  модель не вспомнила — долговечный факт о пользователе теряется навсегда.
  Автоизвлечения из диалога нет;
- у профиля нет обслуживания: дубли и противоречия предпочтений никто не
  замечает (Dream смотрит только на проекты).

Референсы (`docs/reference-analysis.md`): hermes-agent — «nudges» (напоминания
сохранять знание) и `MemoryManager`; nanobot — Dream. Взято выборочно и
адаптировано под single-writer и governance Svarog.

## Ключевые решения (зафиксированы в брейншторме)

1. **Профиль — типизированные секции + персона-директива**, набор
   доменно-нейтральный (агентом пользуется не только разработчик).
2. **Автозахват — прямая запись (Flow A), без proposals.** Безопасность
   переносится в код (jail, консервативные операции, дедуп, git-откат).
3. **Активный nudge убран** — остаётся только пассивная строка в
   `_MEMORY_GUIDE`; extractor — достаточная страховка.
4. **#4 отдельным механизмом не строится** — растворяется в валидации
   контракта (#3) и семантическом проходе Dream (#5).
5. **`autocapture.enabled` и `dream.enabled` — shipped-default `true`.**
   Осознанно отменяет дефолт ADR-0020 (там Dream `false`): гиперперсонализация
   — заявленная фича, работает из коробки; стоимость гасится дешёвой
   aux-моделью, гейтом и дедупом. Оформляется новым ADR.
6. **Единица захвата — сессия, а не ход.** Chat — первоклассный сценарий.

## Решение

### #3 — Контракт профиля и персона-директива

`user/profile.md` получает **распознаваемый (не жёстко обязательный)** набор
H2-секций, поделённый на два класса.

**Поведенческие** — из них код собирает директиву:

- `## Тон` — краткость/подробность, формальность;
- `## Язык` — язык ответов;
- `## Предпочтения` — доменные рабочие предпочтения без привязки к роли (у
  разработчика — стиль кода, у менеджера — формат отчётов/структура, у бизнеса
  — подача выкладок);
- `## Не трогать` — do-not-touch (темы, файлы, области).

**Фактические** — остаются справочным контекстом, как сейчас:

- `## Роль` — кто пользователь и в каком контексте (разработчик / бизнес /
  менеджер), компания; заодно задаёт агенту аудиторию;
- `## Расписание` — TZ, часы, режим;
- `## Прочее` / свободный текст — остальные факты.

**Мягкий контракт:** все секции опциональны; неизвестные H2 разрешены — они
просто не идут в директиву. Профиль без единой распознанной секции валиден
(поведение как сейчас).

**Рендер персона-директивы** (в `context_builder.py`): код парсит профиль,
из поведенческих секций собирает компактный директивный блок и кладёт его в
системный промпт как инструкцию («Отвечай кратко. Язык — русский. Не трогай
…»), **отдельно** от блока «Текущее содержимое памяти» (туда идут фактические
секции и остальная память). Персонализация становится поведением, а не
справкой. Пустые поведенческие секции → директива не рендерится.

- Парсер секций переиспользует секционную логику из `memory/apply.py`
  (`_replace_section`/`has_section`) — выносится в общий хелпер
  (`memory/sections.py` или рядом), чтобы не дублировать.
- Имена секций и их роль дублируются в `_MEMORY_GUIDE`, чтобы модель знала
  их при записи через `remember replace_section`.

**Почему секции, а не frontmatter:** предпочтения — это проза, она плохо
ложится в плоские YAML-поля, но хорошо в секции; `replace_section` уже умеет
обновлять их атомарно.

### #1 — Автозахват фактов о пользователе

Два компонента.

**A. Пассивный nudge.** Строка в `_MEMORY_GUIDE`: «долговечные факты и
предпочтения о пользователе сохраняй в профиль через `remember
replace_section` по нужной секции». Активного корректирующего nudge в ходе
run'а нет.

**B. Aux post-session extractor** — страховочная сеть.

- **Модель:** `models.auxiliary_or_default()` (дешёвая, та же, что у
  curator/компакции). Один вызов, **без tools** — только структурированный
  вывод (JSON-список правок). Отсутствие tools = текст из памяти/диалога не
  управляет исполнением (тот же инвариант, ради которого Dream лишён tools).
- **Единица — сессия, триггер — её граница:**
  - единичный `svarog run`: сессия = один run → extractor срабатывает один
    раз при финализации;
  - chat: extractor запускается на `ChatEngine.close()` — один проход по
    необработанному хвосту сессии. **Никаких вызовов per-turn.**
  - фолбэк от «бесконечной» сессии: если чат идёт долго и не закрывается,
    extractor догоняет по порогу `autocapture.every_n_turns` (~6
    необработанных ходов). Per-session **watermark** (индекс последнего
    обработанного сообщения) двигается после каждого прохода — хвост не
    переобрабатывается.
- **Дешёвый гейт до вызова модели:** пропуск, если в сессии не было ни одного
  пользовательского хода сверх исходной задачи ИЛИ за сессию уже была ручная
  запись в профиль. Не тратим токены на заведомо пустое.
- **Вход модели:** транскрипт сессии (`state.messages` / записанные
  сообщения) + текущий профиль + контракт секций.
- **Запись — прямая (Flow A):** извлечённые факты → `MemoryChangeRequest` →
  штатная очередь writer'а (как `remember`). `AUTOCAPTURE`-origin и
  `max_pending` **не нужны** — их в дизайне нет.

**Рельсы прямой записи** (ревью нет — безопасность в коде):

- extractor пишет **только в `user/profile.md`**; любой факт с иным путём
  отбрасывается (jail);
- операции консервативные: **append / добавление в секцию предпочтительнее**;
  destructive `replace_section` поведенческой секции — только когда факт явно
  опровергает старый, не по любому совпадению темы;
- дедуп против текущего профиля — не писать уже записанное;
- кап `autocapture.max_facts` за проход;
- каждая правка проходит `secret_scan` writer'а и становится отдельным
  git-коммитом с трейлером `Run-Id` → ошибочный автозахват тривиально
  откатывается через git. Это страховка вместо ревью.

### #5 — Dream видит профиль (+ растворённый #4)

- **#4 отдельным аудитом не строится.** У фактов профиля нет дат →
  детерминированной `stale`-логики нет; дубли/противоречия — семантика.
  Валидацию контракта секций даёт запись (#3).
- **Dream расширяется**, чтобы трактовать `user/profile.md` как первоклассную
  страницу. Его семантический проход (`memory/dream.py`, блок `_SEMANTIC`)
  уже ищет «противоречащие утверждения на разных страницах» — добавляется
  явное упоминание профиля: дубли и противоречия в предпочтениях, устаревшие
  факты. Dream по-прежнему **предлагает** (proposals), человек одобряет —
  ревью тут уместно, т.к. это переосмысление, а не свежий факт.
- `dream.enabled: true` как shipped-default (см. новый ADR).

## Конфигурация

Новая `AutocaptureConfig` (`config/schema.py`):

```yaml
autocapture:
  enabled: true           # shipped-default
  max_facts: 5            # кап правок за проход
  every_n_turns: 6        # догоняющий порог для длинных чат-сессий
```

Модель автозахвата — `models.auxiliary_or_default()`, отдельного поля нет.

Изменение существующей `DreamConfig`:

```yaml
dream:
  enabled: true           # было false (ADR-0020) — отменяется новым ADR
```

Инвариант блока D сохраняется: конфиг лишь *заводит* джобу Dream в
`ensure_system_jobs`; живую джобу человек выключает `svarog cron disable`, и
конфиг это решение не перебивает.

## Обработка ошибок

Extractor — best-effort, **никогда не роняет run**:

- сбой aux-вызова / невалидный JSON → warning в лог, ноль записей,
  финализация продолжается;
- битый/непарсируемый профиль → распознанных секций ноль, директива пустая,
  run идёт дальше (reader и парсер устойчивы к мусору);
- факт с несуществующим якорем секции → отсекается штатной `validate_change`
  до постановки в очередь; лог, остальные факты применяются;
- jail: путь строго `user/profile.md`, иначе факт отбрасывается.

## Тестирование

По образцу `tests/test_memory_*.py`, `tests/test_dream_profile.py`:

- **Парсер + рендер директивы:** профиль → ожидаемый директивный блок;
  распознанные/неизвестные секции; пустой профиль → пустая директива.
- **Extractor:** JSON→`MemoryChangeRequest`; дедуп против профиля; кап
  `max_facts`; jail «только профиль»; консервативность операций (append
  предпочтительнее replace).
- **Гейт:** пропуск, когда не было пользовательских ходов / профиль уже
  писали вручную в этой сессии.
- **Триггер:** watermark сессии (close + `every_n_turns`); единичный run
  срабатывает ровно один раз; хвост не переобрабатывается.
- **Интеграция:** реплика с предпочтением в диалоге → после close профиль
  обновлён git-коммитом с `Run-Id`; повтор той же реплики → без дубля.
- **Dream:** `build_dream_task` включает находки по профилю; профиль
  трактуется как страница в семантическом проходе.
- **Конфиг:** дефолты `true`; валидация полей.

## Затрагиваемые файлы

- `runtime/context_builder.py` — рендер персона-директивы, обновление
  `_MEMORY_GUIDE` (имена секций, пассивный nudge).
- `memory/sections.py` (новый) — общий парсер/рендер H2-секций, вынос из
  `memory/apply.py`.
- `memory/profile.py` (новый) — контракт секций профиля + сборка директивы.
- `memory/autocapture.py` (новый) — extractor: гейт, aux-вызов, JSON→changes,
  дедуп, рельсы.
- `runtime/orchestrator.py` — вызов extractor в фазе финализации run'а; проброс
  watermark; пропуск для не-`DEFAULT` профилей.
- `cli/chat_engine.py` — хук `close()` и `every_n_turns`-фолбэк; хранение
  watermark сессии.
- `memory/dream.py` — упоминание профиля в `_SEMANTIC`.
- `config/schema.py` — `AutocaptureConfig`; `DreamConfig.enabled=True`.
- `docs/adr/0021-hyperpersonalization-defaults.md` (новый) — отмена дефолта ADR-0020, обоснование
  гиперперсонализации из коробки.

## Явно вне скоупа

- #2 FTS5-retrieval (связка B, отдельный цикл).
- Векторный поиск / эмбеддинги (нарушает «Git + SQLite», ADR-0001).
- Персонализация нативного `AgentLoop` через vision — отдельная работа.
- Ревью памяти из чата/Telegram (как и в ADR-0020 — вне цикла).
