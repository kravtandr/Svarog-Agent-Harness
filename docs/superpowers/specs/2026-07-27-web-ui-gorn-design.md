# Веб-интерфейс Сварога: «Горн»

**Дата:** 2026-07-27
**Статус:** дизайн утверждён, реализация не начата
**Скоуп:** веб-клиент поверх существующего gateway (`svarog serve`, ADR-0017).
Одна оболочка работает и локально (свой agent-home), и против удалённого
сервера, и на десктопе, и на мобильном. Голосовой ввод и ответ появятся
позже — здесь фиксируются решения, которые влияют на макет и модель данных.
Мультиарендные админ-экраны (тенанты, квоты, чужие runs) — за скоупом,
но каркас их не исключает.

## Проблема

Сварог управляется только из CLI. Три следствия:

- **Порог входа.** Чтобы посмотреть, что агент сделал, нужно знать
  `svarog traces show`, `svarog approvals list`, `svarog memory show`.
- **Конфигурация правится вслепую.** `svarog.yaml` — 24 секции строгой схемы
  (`extra="forbid"`); человек редактирует файл руками, а ошибку видит только
  при следующем запуске.
- **Память нечитаема снаружи.** Она специально сделана человекочитаемым
  markdown в Git, но посмотреть её можно лишь через `svarog memory show`
  или открыв файлы редактором — без поиска, истории и понимания, что из
  этого доедет до модели.

Бэкенд для веба уже есть: gateway отдаёт runs, сессии, approvals, скиллы,
workspaces и стрим событий по WS и NDJSON. Не хватает клиента и нескольких
эндпоинтов.

## Ключевые решения (зафиксированы в брейншторме)

1. **Чат в центре, а не пульт наблюдения.** Рассматривались три каркаса —
   chat-first («Горн»), ops-console («Наковальня») и трёхпанельный верстак
   («Кузница»). Выбран chat-first: для одиночного разработчика на localhost
   пульт полупустой, а разговор — то, через что ставится задача.
2. **Навигатор из «Кузницы».** Слева, помимо истории чатов, постоянные
   разделы: рабочие папки, скиллы, память, настройки.
3. **Знакомо как Claude.** Первый заход выглядел машинным шаблоном
   (почти-чёрный фон плюс неон, пилюли статусов, лейблы капсом, карточка на
   каждый вызов). Второй заход с радикальными языками (светлая ведомость,
   монохромные швы, глоссы на полях) отклонён как избыточный. Принято:
   спокойный тёмный интерфейс, моноширинный только в коде, один акцент.
4. **Вызовы инструментов и MCP — отдельно проработанный элемент**, а не
   побочный вывод. Это то, что видно чаще всего остального.
5. **Конфигурация правится с видимым диффом `svarog.yaml`.** Конфиг живёт
   в файле под Git — интерфейс не должен это скрывать.
6. **Секреты в вебе не показываются и не редактируются.** Только имена и
   факт, что значение найдено (ADR-0006).
7. **Мобильный — второй полноценный режим, а не деградация.** Каждый экран
   принимается сразу на узкой и широкой ширине.
8. **Голос закладывается, но не реализуется сейчас.** Фиксируются четыре
   решения, влияющие на макет и модель событий: распознанное не отправляется
   само, вслух читается только речь агента, гейт голосом не подтверждается,
   речь прерывается вводом.

## Решение

### Каркас

Единая оболочка на всех экранах:

```
┌──────────────┬───────────────────────────────────────────┐
│ Сварог   ⌘K  │ шапка: заголовок · ветка · дифф · счётчики│
│ + Новый чат  ├───────────────────────────────────────────┤
│ рабочая папка│                                           │
│              │  содержимое экрана                        │
│ Сегодня      │                                           │
│  · сессии    │                                           │
│ Вчера        │                                           │
│  · сессии    │                                           │
│              │                                           │
├──────────────┤                                           │
│ Скиллы    14 │                                           │
│ Память    69 │                                           │
│ Настройки    │                                           │
└──────────────┴───────────────────────────────────────────┘
```

Навигация — только через левый столбец и `⌘K`. Отдельного «дашборда» нет:
пустой экран приложения — это новый чат.

### Визуальная система

Тёмная тема, единственная. Токены:

| Токен | Значение | Назначение |
|---|---|---|
| `--bg` | `#1A1917` | фон приложения (тёплый нейтрал, не «почти чёрный») |
| `--surface` | `#211F1D` | навигатор, боковые панели |
| `--raised` | `#292724` | реплика человека, активный пункт, вторичная кнопка |
| `--line` | `#322F2B` | видимая граница (только поле ввода и гейт) |
| `--line-soft` | `#262421` | волосяной разделитель внутри групп |
| `--text` | `#EAE5DC` | основной текст |
| `--muted` | `#A29B90` | вторичный |
| `--faint` | `#6E6862` | подписи, значения по умолчанию |
| `--ember` | `#D2622C` | **акцент** |
| `--ok` / `--bad` / `--git` | `#6E9B72` / `#C4635C` / `#7E93B8` | семантика: прошло, упало, git |

Три правила, которые отличают этот вид от первого захода:

- **Акцент ровно в трёх местах:** активная сессия, гейт разрешения, кнопка
  отправки. Нигде больше. Семантические цвета акцентом не считаются.
- **Моноширинный только там, где код:** пути, команды, диффы, имена
  инструментов, значения конфига. Речь, подписи и элементы управления —
  системным гротеском.
- **Воздух вместо рамок.** Обводка есть у поля ввода и гейта. Всё
  остальное разделено отступом и сдвигом фона.

**Шкала накала** — единственный декоративный приём, который несёт данные:
полоса 2 px слева от сессии кодирует свежесть цветом остывающего металла
(белая — идёт сейчас, дальше `--ember` → тёмная). Заменяет колонку «когда».

### Экран «Диалог»

Лента прижата к низу. Реплика человека — приподнятый блок, ответ агента —
обычный текст. Между ними группа вызовов (ниже) и, при остановке политикой,
гейт разрешения.

**Гейт** — единственное акцентное пятно в ленте. Показывает команду
моноширинным, три действия (`Разрешить`, `Разрешать такие до конца чата`,
`Отклонить`) и правило, по которому агент остановился, — решение принимается
со знанием причины. Соответствует `POST /approvals/{id}`; вопросы `ask_user`
рендерятся тем же блоком с полем ответа (`/approvals/{id}/answer`).

**Поле ввода** несёт режимы под строкой: автономия, исполнитель, модель —
прямой перенос `/policies`, `/executor`, `/mode` из CLI. Подсказки `/`, `@`,
`⌘K` — под полем.

**Шапка** показывает ветку задачи и накопленный дифф (`GET /runs/{id}/diff`);
нажатие раскрывает изменения поверх диалога, не уводя из чата.

### Вызовы инструментов и MCP

Отдельно специфицированный элемент — он встречается чаще всего.

**Свёрнутое состояние — всегда одна строка одинаковой формы:**

```
[отметка] [сервер/]имя  аргумент …                       результат  ›
```

Подряд идущие вызовы сцеплены в одну группу с общим фоном и разделены
волосяной линией: карточки на каждый вызов нет.

- **Отметка исхода** слева: `✓` выполнено, `▸` идёт, `✕` упало.
- **Инструмент с MCP-сервера** отличается только именем сервера перед
  названием: `github/list_issues`, `postgres/query`. Значков и подписи «MCP»
  нет — важно, что вызвано, а не по какому протоколу.
- **Справа всегда результат**, а не слово «успешно»: `+58 −4`, `3 записи`,
  `код 1`, хеш коммита. Источник — `ToolCallView` плюс события стрима.
- **Раскрытие внутри группы**, прокрутка удерживает низ: лента не прыгает.
  Раскрытый вид показывает запрос и ответ.
- **Упавший вызов раскрыт изначально.** Прятать причину остановки бессмысленно.
- Хвост длинной группы сворачивается в строку «Ещё N шагов».

### Экран «Настройки»

Три колонки: разделы, форма, дифф.

Форма собирается **из той же схемы Pydantic**, по которой Сварог читает
конфиг (`config/schema.py`): поля, типы и пределы — оттуда же. Форма не может
предложить настройку, которую конфиг отвергнет.

Справа постоянно виден дифф `agent-home/svarog.yaml` — во что превратится
форма. Ничего не записывается до `Сохранить`. Это снимает главный страх
правки конфига через интерфейс: непонятно, что уедет в файл.

**Секреты:** экран показывает имена, найдено ли значение и откуда (файл или
переменная окружения). Значение не показывается и не редактируется в вебе;
задать его по-прежнему можно только `svarog secrets set` или через env.

### Экран «Память»

Три колонки: дерево с поиском, документ, боковая панель.

- **Поиск идёт через `search_memory`** — тот же механизм, которым агент
  находит записи сам. Если он что-то не нашёл, это воспроизводится здесь.
- **Документ** рендерится как markdown с подсветкой совпадений.
- **Боковая панель:** полоса «сколько памяти доедет до контекста следующего
  запуска» (единственный честный ответ на «агент забыл» — обычно не забыл,
  а не влез), история правок настоящими коммитами с автором (агент или
  человек) и откат к любому из них.

### Состояния

Для каждого экрана обязательны: загрузка, пусто, ошибка соединения,
отсутствие прав. Пустой экран — приглашение к действию, не «нет данных»:
у памяти — «Сварог запишет сюда первые решения после первой задачи».

## Привязка к gateway API

### Уже есть (ADR-0017)

| Экран | Эндпоинт |
|---|---|
| Отправка сообщения | `POST /sessions/{id}/messages` |
| Создание сессии | `POST /sessions`, `GET /sessions/{id}` |
| Стрим ленты | `WS /runs/{id}/events`, `GET /runs/{id}/events/stream` |
| Шаги и вызовы | `GET /runs/{id}` (`RunDetail.tool_calls`, `messages`) |
| Дифф в шапке | `GET /runs/{id}/diff` |
| Прервать | `POST /runs/{id}/cancel`, `POST /runs/{id}/resume` |
| Гейт | `GET /approvals`, `POST /approvals/{id}`, `/answer` |
| Скиллы | `GET /skills` |
| Рабочие папки | `GET /workspaces`, `/{name}/files` |
| Шапка, квота | `GET /whoami` |

### Чего не хватает — новые эндпоинты

Это дельта к серверу, которую придётся реализовать вместе с UI:

1. **`GET /sessions`** — списка сессий нет вовсе, есть только создание и
   получение по id. Без него левый столбец нечем наполнить.
2. **`GET /sessions/{id}/messages`** — воспроизведение ленты при открытии
   старой сессии. Сейчас история достаётся только по каждому run'у отдельно.
3. **Конфигурация:** `GET /config` (значения плюс схема), `POST /config/preview`
   (дифф без записи), `POST /config` (запись). Схему отдавать из Pydantic —
   форма не должна дублировать её на клиенте.
4. **Секреты:** `GET /secrets` — только имена и признак «значение найдено».
5. **Память:** `GET /memory/tree`, `GET /memory/file?path=`,
   `GET /memory/search?q=` (обёртка над `MemoryIndex.search`),
   `GET /memory/history?path=`, `POST /memory/revert`.
6. **CORS и раздача статики.** `CORSMiddleware` в gateway не подключён.
   В бою статика едет с того же origin, что и API, — CORS не нужен; он нужен
   для режима разработки, когда Vite поднимает свой dev-сервер на другом порту.
   Плюс сама раздача собранного бандла из `svarog serve`.

Каждый пункт — отдельный шаг плана реализации, UI на них не блокируется:
экраны можно вести по одному вместе с их эндпоинтами.

## Адаптивность: мобильный и десктоп

Мобильный — не деградация десктопа, а второй полноценный режим. Каркас
«Горна» к этому приспособлен: он состоит из одной ленты и одного навигатора,
и на узком экране навигатор просто уходит в выдвижную панель.

**Точки перелома:**

| Ширина | Раскладка |
|---|---|
| ≥ 1240 | три колонки там, где они есть: навигатор + содержимое + боковая панель |
| 900–1239 | боковая панель схлопывается в раскрываемый блок под содержимым |
| < 900 | одна колонка; навигатор — выдвижная панель по жесту или кнопке |

**Что меняется на узком экране:**

- **Навигатор** открывается поверх содержимого и закрывается по выбору
  сессии. История чатов на мобильном — полноэкранный список с поиском.
- **Шапка** сжимается до заголовка и ветки; счётчики шагов, токенов и дифф
  переезжают в раскрываемую полоску под ней.
- **Поле ввода** прижато к низу и поднимается над клавиатурой; переключатели
  режимов (автономия, исполнитель, модель) сворачиваются в одну строку
  «под надзором · нативный · qwen3-coder», раскрываемую нажатием.
- **Вызовы инструментов** получают двухстрочный вариант: первая строка —
  отметка, имя и результат, вторая — аргумент приглушённым. Обрезать
  результат ради аргумента нельзя: результат важнее.
- **Гейт разрешения** — кнопки на всю ширину в столбик, `Разрешить` первой.
  Правило политики переносится под кнопки.
- **Настройки:** одна колонка; дифф `svarog.yaml` открывается нижней шторкой
  по кнопке «Показать изменения (2)», а не занимает треть экрана.
- **Память:** дерево — в выдвижной панели, боковая панель разворачивается
  секциями под документом.

Целевой минимум — 360 px. Горизонтальной прокрутки страницы нет ни на одной
ширине; прокручиваться внутри своего контейнера имеют право только диффы,
вывод команд и длинные пути.

## Голосовой ввод и ответ

Не реализуется в этой итерации, но закладывается сейчас: доделать это поверх
готового интерфейса дороже, чем оставить место заранее.

**Что резервируется в макете:**

- **Кнопка микрофона в поле ввода**, рядом с отправкой. Место под неё
  выделено с самого начала, чтобы потом не переверстывать композер.
- **Управление воспроизведением у каждой реплики агента** — появляется по
  наведению или удержанию, как «копировать».

**Решения, которые нужно принять сейчас, потому что они влияют на модель данных:**

1. **Распознанная речь попадает в поле ввода как редактируемый текст и не
   отправляется сама.** Сварог выполняет команды в репозитории; отправка по
   тишине или по слову-триггеру — способ запустить не то, что имелось в виду.
2. **Вслух читается только речь агента, не действия.** Зачитывать
   `write_file memory/index.py +58 −4` бессмысленно. Это требует, чтобы
   рендерер отличал реплику от вызова, — в принятой структуре ленты это уже
   так, и разделение нужно сохранить при нормализации событий стрима.
3. **Гейт разрешения голосом не подтверждается.** Решение по команде среднего
   и высокого риска требует нажатия. Голосом можно попросить прочитать, что
   именно предлагается.
4. **Речь прерывается по началу ввода** — голосового или обычного.

**Чем это делается.** Первая реализация — браузерный Web Speech API:
распознавание и синтез на стороне клиента, без единой новой зависимости на
сервере. Это сохраняет ограничение ADR-0001 (из инфраструктуры только Git и
SQLite). Серверный STT/TTS означал бы внешний сервис или локальную модель —
отдельное решение, которое здесь не принимается.

## Локальный режим против удалённого

Оболочка одна. Различие — в источнике данных: локально UI ходит в свой
gateway на `127.0.0.1`, удалённо — по профилю `remote` с bearer-токеном
(ADR-0017 §3). В шапке видно, к чему подключены. Мультиарендные экраны
появляются только при подключении к серверу и в этом спеке не описаны.

## Вне скоупа

- Скиллы (карточки, proposals, curate), трейсы запусков, очередь approvals
  отдельным экраном, тенанты и квоты. Они собираются из тех же деталей;
  рисовать их следует после того, как язык утвердится на трёх экранах.
- Светлая тема.
- **Реализация** голосового ввода и ответа: в этой итерации только
  подготовка макета и модели событий (см. соответствующий раздел).

## Риски

- **Дельта API больше самого UI.** Шесть пунктов выше — это работа на сервере,
  и она может оказаться дороже клиента. Смягчение: вести экраны по одному,
  каждый со своими эндпоинтами, а не всё сразу.
- **Схема конфига строгая, а форма — приблизительная.** Если генерировать
  форму не из схемы, а руками, они разъедутся при первом же новом поле.
  Поэтому схема отдаётся с сервера, а не дублируется на клиенте.
- **Стрим и воспроизведение — два разных источника** одной и той же ленты
  (WS для живого, `RunDetail` для истории). Расхождение в форматах даст
  «прыгающую» ленту при переоткрытии сессии. Нужен один рендерер и общая
  нормализация события. Это же нормализованное событие потом определяет,
  что читать вслух, — расхождение обойдётся дважды.
- **Мобильный режим правится последним и потому ломается.** Смягчение:
  каждый экран принимается сразу на трёх ширинах, а не «потом причешем».
- **Голос упирается в браузер.** Web Speech API поддержан неровно, а на
  части платформ распознавание уходит в облако производителя. Это нужно
  сказать пользователю в момент включения микрофона, а не в документации.

## Проверка

- Каждый экран снимается на ширинах **360, 768, 1100, 1440**; горизонтальной
  прокрутки страницы нет ни на одной. Прокрутка внутри контейнера допустима
  только у диффов, вывода команд и длинных путей.
- На узком экране: навигатор открывается и закрывается, поле ввода не
  перекрывается клавиатурой, кнопки гейта нажимаются пальцем (цель ≥ 44 px).
- Клавиатура: `⌘K`, отправка, решение по гейту достижимы без мыши, фокус
  виден.
- Живая лента и воспроизведённая из истории дают одинаковый результат для
  одного и того же run'а.
- Конфиг: изменение в форме даёт дифф, совпадающий с тем, что реально
  запишется в `svarog.yaml`; отказ схемы показывается на поле, а не общим
  сообщением.
- Секреты: в ответах API и в DOM нет ни одного значения секрета.
- Место под микрофон и управление воспроизведением присутствует в макете
  композера и реплики, даже пока функция выключена, — чтобы включение не
  потребовало переверстки.

## Стек клиента

**Vite + React + TypeScript.** Рассматривался также вариант Jinja + HTMX + SSE
прямо из FastAPI — он не добавляет в репозиторий второго языка, но мобильные
жесты, командная палитра, удержание прокрутки при раскрытии вызовов и
последующий голосовой ввод обошлись бы там дороже, чем сэкономили: голос всё
равно требует клиентского кода.

Ограничение ADR-0001 («из инфраструктуры только Git и SQLite») касается
**runtime**, а не сборки, и не нарушается:

- Бандл собирается в CI и едет готовым внутри extra `server`.
  **Запуск Сварога Node не требует** — `uv sync --extra server` и `svarog serve`
  достаточно.
- Node нужен только для разработки самого клиента.
- Статика раздаётся тем же `svarog serve` с того же origin, поэтому CORS
  нужен лишь для режима раздельной разработки (Vite dev-server на другом
  порту) и для сторонних клиентов.

Исходники клиента — в `web/` в этом же репозитории: контракт API и UI
меняются вместе, разносить их по репозиториям на этом этапе преждевременно.
