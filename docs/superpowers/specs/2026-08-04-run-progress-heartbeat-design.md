# Live-прогресс run'а: секундомер и токены в строке «Сварог работает…»

**Дата:** 2026-08-04
**Статус:** утверждено

## Задача

Пока внешний executor (opencode / claude-code / codex) думает над ходом, WS-стрим run'а молчит: адаптер шлёт `text`-события только целыми репликами (`runtime/external.py:318`), а строка «Сварог работает…» в чате гаснет по первому же событию (`web/src/screens/ChatScreen.tsx:295`). Первый ход агента может занимать минуты — выглядит как зависание.

Нужно: (1) секундомер рядом со статусом, (2) трансляция уже потреблённых токенов/стоимости по ходу run'а.

Ускорение старта контейнеров в объём **не входит** по результатам замера (см. «Замер» ниже): вся docker-обвязка занимает ~0.7 с и узким местом не является.

## Замер старта sandbox (3 итерации, образ svarog/agent-opencode)

Полная цепочка `AgentNetwork.start` + `DockerEnvironment.start` с боевыми флагами:

| Фаза | Время |
|---|---|
| `network create --internal` | 0.04–0.05 с |
| relay-контейнер (`docker run -d`) | 0.11–0.13 с |
| `network connect bridge` | 0.03 с |
| agent-контейнер (`docker run -d`) | 0.11–0.12 с |
| первый `docker exec` CLI | 0.27–0.41 с |
| **Итого** | **0.56–0.75 с** |

Мёртвое время до первого события — это загрузка CLI агента + MCP-хендшейк + латентность первого LLM-ответа, не контейнеры. Warm-сессии (TTL 900 с, `config/schema.py:265`) уже переиспользуют sandbox между сообщениями сессии.

## Решение

### Источник данных

Bridge-прокси — источник истины usage внешнего run'а (ADR-0016 §3): `bridge.usage.input_tokens/output_tokens` пополняются после каждого завершённого LLM-запроса агента (`runtime/bridge.py:316`). Хук `RunHooks.on_progress` уже существует (`runtime/run_assembly.py:106`) и зовётся нативным loop'ом после каждой итерации (`runtime/loop.py:396`), но gateway его не подключает, а внешний executor зовёт один раз в конце.

### Событие

Новый тип WS-события run'а:

```json
{"type": "progress", "iterations": 3, "tokens": 12400, "cost_usd": 0.04}
```

### Backend

1. **`runtime/external.py`** — в `_execute` на время `_stream_with_suspend` поднимается фоновый ticker-task (период 2 с): читает `self._bridge.usage` и, **только если счётчики изменились** с прошлой эмиссии, зовёт `self._on_progress(state.tool_calls, total_tokens, cost_usd, 0.0, 0)` (доля контекста и cached неизвестны — 0, как в существующем вызове `external.py:403`). Отмена ticker'а гарантируется `finally`. Без bridge (`self._bridge is None`) или без `_on_progress` ticker не поднимается.

   Эмиссия «только при изменении» обязательна: история событий для WS-реплея ограничена 2000 записями (`storage/events.py:57`); безусловный тик за долгий run вытеснил бы настоящие события. Число эмиссий ограничено числом LLM-запросов агента.

2. **`gateway/service.py`** `_event_hooks` — подключить:

   ```python
   on_progress=lambda it, tokens, cost, ctx, cached: emit(
       {"type": "progress", "iterations": it, "tokens": tokens, "cost_usd": cost}
   )
   ```

   Нативные run'ы получают прогресс автоматически (loop уже зовёт хук).

### Frontend

1. **`web/src/model/thread.ts`** — в `StreamEvent` добавляется вариант `{ type: "progress"; iterations: number; tokens: number; cost_usd: number }`. `applyEvent` его игнорирует (ленту не трогает) — прогресс живёт отдельным состоянием экрана.
2. **`web/src/screens/ChatScreen.tsx`**:
   - строка статуса показывается всё время `running` (не только до первого события): «Сварог работает… 1:23 · 12 400 токенов · $0.04»;
   - секундомер — локальный интервал (1 с) от момента отправки сообщения; для live-run'а, подхваченного при открытии чата (`thread.live_run_id`), — от момента подписки;
   - обработчик в `watch`: `progress`-событие обновляет состояние счётчика и не передаётся в `applyEvent`; прочие события, как и раньше, гасят `thinking`;
   - токены/стоимость появляются в строке только после первого `progress` (до него — просто «Сварог работает… 0:07»); стоимость скрывается, пока равна 0.
3. Пересборка `web/dist` обязательна (известная ловушка: фича «не видна в UI» = бандл не пересобран).

## Обработка ошибок

Ticker обёрнут так, что исключение внутри (гонка чтения usage, упавший колбэк) логируется и не роняет run. `progress` после `run_finished` невозможен: ticker отменяется до публикации финала. Незнакомое событие старым бандлом UI игнорируется молча (switch по `type` без default-ветки) — деплой бэкенда раньше фронта безопасен.

## Тесты

- Юнит `external.py`: ticker эмитит при изменении usage и молчит без изменений; отменяется по завершении стрима; без bridge не поднимается.
- Юнит `service.py`: `_event_hooks().on_progress` публикует событие `progress` с полями.
- Фронтенд: `applyEvent` игнорирует `progress`; строка статуса рендерит секундомер и токены; `progress` не гасит `thinking`.

## Вне объёма

- Live-токены внутри одного LLM-запроса (инкрементальный парсинг SSE в `_UsageMeter`) — отдельная фича, работает только для anthropic-формата.
- Ускорение docker-старта (параллельный запуск relay и agent-контейнера, ~0.2 с выигрыша).
- Прогресс в Telegram-интерфейсе и CLI.
