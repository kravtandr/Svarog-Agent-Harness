# Прогон 2026-07-27 — retrieval памяти по содержимому (S34–S38, native)

**Цель:** первый прогон сценариев связки B (`search_memory` + авто-инъекция
релевантного, ветка `feat/memory-fts-retrieval`) на реальном агенте — проверить,
что механика работает и что сами сценарии исполнимы.

**Среда:** рецепт README §2, четыре изолированных `/tmp/svarog-s3*`; sandbox
`local-trusted`, executor native; модель `deepseek/deepseek-v4-flash` через
OpenRouter. `HEAD=29bc2b9`.

| Сценарий | Итог | Ключевое |
|---|---|---|
| S34 поиск по телу | **ЗЕЛЁНЫЙ** | `search_memory` → `read_memory` → верное число из памяти |
| S35 промах по словоформе | **ЗЕЛЁНЫЙ** по жёсткому критерию | поиск промахнулся; спас перебор по маленькому корпусу |
| S36 авто-инъекция | **ЗЕЛЁНЫЙ** | блок доехал до промпта, агент им воспользовался |
| S37 recall через память | **ЗЕЛЁНЫЙ** с оговоркой | порядок обратный: `read_memory` раньше `search_memory` |
| S38 расследование | **ЗЕЛЁНЫЙ** | 2 разных поиска → 2 разные страницы, противоречие названо |

**Главный результат — не баг, а поведенческая закономерность.** Агент
систематически предпочитает угадать путь по `index.md` и прочитать страницу
целиком, вместо того чтобы искать. В S34/S35/S37 `search_memory` был вызван, но
решающим оказался `read_memory` по угаданному пути. Это рационально: пока
`index.md` перечисляет все страницы, поиск не нужен. Ценность связки B
проявляется ровно там, где каталог перестаёт помещаться в контекст — и в S36,
единственном сценарии с переполнением, поиск сработал безупречно. Дизайнерское
решение «авто-инъекция только при переполнении» этим прогоном подтверждено.

**Оговорка про надёжность.** По одному прогону на сценарий (спеки просят 2–3).
Выводы про механику доказательны, выводы про поведение модели — нет.

## S34 — поиск по содержимому, когда заголовок не помогает

Память из 5 страниц через writer; факт про ретраи спрятан в секции «Интеграции»
страницы Billing, в `index.md` она описана как «платежи и счета» — по заголовкам
не найти. Проверено перед прогоном.

Траектория (`run d211388b`, 5 итераций):
`search_memory query=ретраи эквайринг retry acquirer` → `read_memory
projects/billing/overview.md` → ответ «максимум попыток 5» со ссылкой на секцию.

Assert выполнен целиком. Агент сам отметил, что деталей (задержка, множитель) в
памяти нет — не додумал.

**Наблюдение:** 3 из 5 итераций ушли на `Grep`/`Glob` по пустому workspace в
поисках реализации. Не нарушение (файловые tools ограничены workspace, память им
недоступна), но заметная трата итераций.

## S35 — промах по словоформе и переформулировка

Setup специально выстроен так, чтобы поиск промахнулся: на странице «платежи
выверяются по счетам», вопрос — про «сверку счетов». Ground truth перед
прогоном: `сверка счетов` → 0, `выверка платежей` → 0, `платежи по счетам` →
находит.

Траектория (`run 86b707eb`, 5 итераций): `read_memory
projects/billing/overview.md` **и** `search_memory query=сверка счетов
reconciliation` в первой же итерации, затем `read_memory` двух оставшихся
страниц.

**Жёсткий критерий выполнен:** агент процитировал точную строку из памяти и
честно сказал, что схемы сверки не сохранялось. Галлюцинации не было.

**Но поиск промахнулся ровно как предсказано**, и агента спас перебор: корпус из
трёх страниц позволяет прочитать всё. На памяти в сотни страниц этот путь
закрыт, и тот же промах стал бы провалом.

Метрика сценария: вызов `search_memory` **один**, переформулировки после пустой
выдачи **не было**. Подсказка в описании tool'а («повтори корнем слова или
синонимом») сработала лишь превентивно — агент сам добавил в первый запрос
английский синоним `reconciliation` — но на повтор не подтолкнула.

## S36 — релевантное всплывает из свёрнутого хвоста индекса

31 страница, `index_max_lines: 20`. Целевая страница `projects/telemetry/` —
самая старая по `updated` (2026-01-05), гарантированно в отрезанном хвосте.
Предусловия проверены: `index.md` ровно 20 строк со строкой «и ещё», слова
`telemetry` в нём нет, `index_overflowed=True`, блок строится (264 байта),
контроль при `max_lines=200` даёт пустую строку.

Траектория (`run 36040fba`, 3 итерации): два `search_memory` → `read_memory
projects/telemetry/overview.md` → точный ответ «один к ста, ошибочные запросы
полностью».

Проверка системного промпта прогона (таблица `messages`):

```
# Релевантно задаче (по поиску в памяти)
- projects/telemetry/overview.md — …## Решение [трейсы] [сэмплируем] один к ста…
```

Профиль и свёрнутый `index.md` в промпте остались — блок дополнил навигацию, а
не вытеснил её. Целевая страница видна агенту **только** через инъекцию.

Assert выполнен целиком. Это сценарий, ради которого связка B и делалась.

## S37 — recall через персистентную память, а не через сессию

**Ход 1** (`run 8978f227`): агент создал `decisions/webhooks-retry.md`. В git оба
коммита — заявка `3506bf1` и `memory: reindex` `8b3c9f8`. В `memory_fts` ровно
новая страница; `index.md`, `log.md`, `user/profile.md` исключены. Оба
`search_memory` хода 1 вернули пусто — корректно, память была пуста.

**Ход 2** (`run f00bfe31`, новый run, контекста диалога нет): `read_memory
decisions/webhooks-retry.md` → `search_memory query=вебхук webhook
недоставленный dead letter queue` → ответ с фактами из памяти (backoff+jitter,
6 попыток, DLQ). `svarog memory curate` — находок нет.

`search_memory` **нашёл** страницу. Но Assert требовал порядка «сначала поиск,
затем чтение», а агент сделал наоборот: угадал путь по `index.md`, прочитал, и
только потом подтвердил поиском. Цель сценария (recall из персистентной памяти)
достигнута, буква Assert — нет.

**Наблюдение:** агент дописал в страницу секцию «## Дата — 2025-04-01», которой
в реплике пользователя не было, и год при этом неверный. Выдуманная
метаданность — кандидат в отдельный сценарий.

## S38 — многошаговое расследование с противоречием

Корпус из трёх страниц, полной картины нет ни на одной: решение «через
заголовок», шлюз «из пути /v1/», заметка встречи «путь до конца года, потом
заголовок».

Три хода в `chat --plain`. Итог (7 итераций на последнем ходе):

| Assert | Факт |
|---|---|
| ≥2 `search_memory` с разными запросами | ✅ `версионирование API version` → `decisions/api-versioning.md`; `версионирование шлюз v1 путь` → `projects/gateway/overview.md` |
| ≥2 `read_memory` по разным путям | ✅ 8 вызовов, 4 разных пути (все три страницы + профиль) |
| противоречие названо, не выбрана одна версия | ✅ агент объяснил: решение не отменено, а отложено; источник каши — необновлённый `decisions` |
| итог записан через `remember`, применён в git | ✅ `a024c32` replace_section + `4ba14c5` append |
| `memory curate` чист | ✅ находок нет |
| `write_file` вместо `remember` не вызывался | ✅ |

Итоговая страница содержит статус «переходный период», текущий способ, целевой
способ и обоснование со ссылкой на встречу — то есть обе стороны противоречия и
решение из третьего источника.

Здесь `search_memory` отработал как задумано: два разных запроса нашли две
разные страницы. Показательно, что именно в самом сложном сценарии поиск
оказался востребован.

**Наблюдение:** агент по своей инициативе дописал в `user/profile.md` строку
«Предпочитает русский язык» (коммит `4c4b929`), чего не просили. Поведение
пограничное между полезной персонализацией и самоуправством — стоит отдельного
сценария.
